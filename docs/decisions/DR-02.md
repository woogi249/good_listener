# DR-02: CLI 호출 레이턴시 (end-to-end 역산)

**상태:** 작업 가설 (Phase 0 spike 전)
**작성일:** 2026-04-19
**선행 조건:** DR-00b (rate limit 허용 확인), DR-01 (동시성 모델 확정)

---

## 1. 가정 (Assumption)

- DR-00b에서 시간당 60회 호출이 Pro/Max 구독 rate limit 내에서 허용됨을 확인했다.
- DR-01에서 CLI 동시 호출 가능성 및 큐/풀 모델이 확정된 상태다.
- End-to-end 목표: 발화 종료 시점부터 패널 갱신까지 **≤ 10초** (실시간 체감 상한).
- 프롬프트 토큰: 롤링 버퍼 10~20 발화 × 평균 50 토큰 = **500~1,000 토큰**.
- 출력 토큰: 1줄 50자 제약 준수 시 **50~80 토큰**.
- CLI 프로세스 오버헤드(프로세스 생성·인증·stdout 수신): **150~300ms** 추가.
- 의존성: DR-00b, DR-01. 이 DR 결과는 DR-03(STT 예산 재배분), DR-05(트리거 쿨다운 재계산), DR-06(UX 로딩 표시)에 영향을 준다.

---

## 2. 작업 가설 (Working Hypothesis)

End-to-end 10초 예산을 아래와 같이 배분하고, CLI 구간에 5초를 할당한다.

| 구간 | 할당 시간 | 비고 |
|------|----------|------|
| STT 지연 | 3.0초 | DR-03에서 재검증. Whisper large-v3 GPU 기준 근사치 |
| 트리거 판정 | < 0.1초 | 룰 기반 정규식·카운터 |
| **CLI 호출 왕복** | **5.0초** (p50 3초, p95 5초) | 본 DR의 검증 대상 |
| UI 렌더링 / WebSocket | 1.0초 | 브라우저 렌더링 + 로컬 WS 왕복 |
| 마진 | 0.9초 | 네트워크 변동·OS 스케줄링 완충 |
| **합계** | **10.0초** | |

**통과 기준 (가설):** CLI 구간 **p50 ≤ 3초 AND p95 ≤ 5초**.

이 가설은 Phase 0 spike 실측 결과에 따라 확정 또는 기각된다.

### CPU-only 경로 병렬 예산 (DR-00c Fallback 대응)

DR-00c에서 GPU 없이 CPU-only 환경으로 판정되면 STT 구간이 3초로 수렴하지 않는다. DR-03 Fallback의 medium 모델 + int8 양자화 경로에서 STT p95 ≒ 5초를 전제로, **별도 예산 테이블**을 적용한다.

| 구간 | GPU 경로 (기본) | CPU-only 경로 (Fallback) |
|------|----------------|--------------------------|
| STT 지연 | 3.0초 | 5.0초 |
| 트리거 판정 | <0.1초 | <0.1초 |
| CLI 호출 왕복 | 5.0초 | 5.0초 |
| UI 렌더링/WebSocket | 1.0초 | 1.0초 |
| 마진 | 0.9초 | 0.9초 |
| **end-to-end 합계** | **10.0초** | **12.0초** |

CPU-only 경로에서는 **end-to-end 상한을 12초로 재협상**하며, UI는 Plan C("분석 중" 인디케이터)를 기본 활성화한다. 12초 초과 시 CONSISTENCY.md T-01이 재발동하며, 이 경우 DR-03 탈락 플랜 C(유료 STT 전환) 또는 DR-02 플랜 C(end-to-end 15초 완화)로 즉시 이행한다.

## 3. 이유 (Rationale)

**10초 상한 근거**

Nielsen(1993)의 응답 시간 연구에서 "10초 이내는 대화 흐름을 끊지 않는 상한"으로 정의된다. 회의 중 패널이 10초 내에 갱신되지 않으면 발화 맥락이 이미 진행된 다음 주제로 넘어가 패널 유용성이 급락한다. 15초 이상은 참가자가 화면을 무시하게 만드는 경험적 임계치로 알려져 있다.

**STT 3초 할당 근거**

faster-whisper large-v3를 GPU(VRAM 6GB 이상) 환경에서 실행 시 15초 분량 오디오의 전사 시간이 2~4초 범위로 보고된다. DR-03에서 실측 후 재배분할 예비 수치다.

**CLI 5초 할당 근거 (AGENTS.md "≤ 5초" 재정당화)**

AGENTS.md의 "CLI 호출 왕복 레이턴시 ≤ 5초"는 end-to-end 역산 없이 기재된 숫자였다. 본 DR은 위 예산 배분표에서 10초 목표 - STT(3초) - 트리거(0.1초) - UI(1초) - 마진(0.9초) = **5초** 를 역산하여 해당 수치를 재정당화한다. Claude API 평균 응답 시간(입력 500~1,000토큰, 출력 50~80토큰 기준 약 2~4초)에 CLI 프로세스 오버헤드 150~300ms를 더하면 p50 약 2.5~3초, p95 약 4~5초가 예상 범위다.

**마진 0.9초 설정 근거**

Wi-Fi 전환·OS 스케줄링 지연·Python 인터프리터 초기화 등 측정 외 변동 요소를 흡수하기 위한 완충값이다. 예산이 10초를 초과하지 않는 최소 마진으로 설정했다.

## 4. 검증 방법 (Verification)

- **측정 도구:** Python `time.perf_counter` + `subprocess.run` 래퍼 (DR-00b 스크립트 재사용). **CLI 호출은 반드시 stdin pipe 방식**(`["claude","-p","-"], input=PROMPT`) 사용 — 명령줄 인자 방식은 `ps aux` 노출 취약(CONSISTENCY.md S-1).
- **측정 횟수 (N):** 총 60회 — 버퍼 크기별 20회씩 3구간 (10발화 / 15발화 / 20발화)
- **대표값:** **p50 AND p95** (단일 평균 사용 금지 — 분산이 크므로 꼬리 레이턴시가 사용자 체감에 직접 영향)
- **환경 조건 (고정):** `CONSISTENCY.md §3.7 공통 환경 조건` 참조. 변경 시 세 DR(00b/01/02) 동시 갱신 필수.
  - DR-02 특이 조건: 버퍼 크기별 3구간(10/15/20 발화) × 20회 = 총 60회, 시간대별 분산 평가 위해 오전/오후 각 30회 분리 실행.
- **수집 지표:**
  - 호출별 왕복 시간 (ms)
  - 프롬프트 토큰 크기별 레이턴시 회귀선 (토큰 수 vs 시간 상관관계)
  - 에러 발생 시 재시도까지 소요 시간
  - 시간대별 분산 (오전 vs 오후 비교)
- **통과 기준 (조건부 3단계):**

  | 결과 | 판정 | 후속 조치 |
  |------|------|----------|
  | p50 ≤ 3초 AND p95 ≤ 5초 | 가설 확정 | DR-03 이후 진행 |
  | p50 ≤ 3초 AND p95 ≤ 7초 | 회색 — 마진 재배분 검토 | STT 예산 2.5초로 단축, 마진 0.4초로 축소 후 DR-03 재조정 |
  | p95 > 7초 | 가설 기각 | 탈락 시 대안 실행 |

## 5. 탈락 시 대안 (Fallback)

**탈락 조건:** p95 > 7초

### p95 7~10초 구간

- **플랜 A — 버퍼 축소 + 프롬프트 토큰 감축**
  - 롤링 버퍼를 10발화 → 5발화로 줄여 프롬프트 토큰 500 이하로 제한.
  - 예상 효과: p95 1~2초 단축 (토큰-레이턴시 회귀선으로 추정).
  - 트레이드오프: 요약 품질 저하, 맥락 손실 위험.

- **플랜 B — 스트리밍 출력으로 첫 토큰 지연 우선화**
  - `claude` CLI 스트리밍 옵션 활성화 시 전체 응답 완료 전 첫 토큰을 UI에 표시.
  - 체감 지연은 줄어들지만, 1줄 50자 제약 강제 시점이 출력 완료 후로 지연됨.
  - 구현 복잡도 증가 (부분 출력 파싱 로직 필요).

### p95 > 10초 구간

- **플랜 C — End-to-end 목표 10초 → 15초로 완화**
  - UI에 "분석 중" 로딩 인디케이터 추가로 사용자 체감 완충.
  - DR-06(UX) 로딩 표시 요건 상향 반영 필요.
  - 트레이드오프: 회의 흐름과의 동기화 약화, 핵심 가치 저하.

- **플랜 D — API 직접 호출 전환**
  - CLAUDE.md 최상위 제약("API 직접 호출 금지") 완화를 사용자에게 명시 요청.
  - CLI 프로세스 오버헤드 150~300ms 제거로 p95 약 1~2초 단축 기대.
  - 비용 발생 (시간당 약 $0.05~0.10, DR-00b 플랜 B 추정치 참조 — DR-00b 비용 재계산 시 본 항목도 갱신 필요).
  - **API 키 관리**: DR-00b 플랜 B와 동일 규약 준수 (환경변수 `ANTHROPIC_API_KEY` 전용, 하드코딩·저장소 포함 금지, `.env` 사용 시 `.gitignore` 포함). 상세는 DR-00b 섹션 5 참조.
  - 의사결정권자: 사용자. 사용자 승인 없이 전환 금지.

**영향받는 DR:**
- DR-03 (STT): 플랜 A 채택 시 STT 예산을 3초 → 3.5초로 재배분 가능.
- DR-05 (트리거 쿨다운): 플랜 A 채택 시 버퍼 크기 변경에 따라 쿨다운 기본값 재계산 필요.
- DR-06 (UX 로딩 표시): 플랜 B·C 채택 시 스트리밍 인디케이터 설계 요건 추가.
