# DR-07: 도메인 용어집 + 세션 시작 인터뷰

**상태:** 작업 가설 (Phase 0 spike 전, 선(先) 설계)
**작성일:** 2026-04-22
**선행 조건:** DR-03 (STT 모드), DR-04 (데이터 흐름), DR-05 (트리거 빈도)

## 1. 가정 (Assumption)

- **실측 (2026-04-22):** 동일 WAV 기준 faster-whisper `small`(int8)과 `medium`(int8) 모두 한국어 크립토 도메인 고유명사 오인식 확인.
  - "바이낸스" → `파이넌스` (small·medium 동일 실패)
  - "차익거래" → `차잇거래` (small 실패, medium 복구)
  - `medium` 로드 시간 32.9s, 24초 음성 전사 14.4s (CPU int8)
- Whisper의 `initial_prompt` 파라미터는 ~224 토큰 한도 내에서 어휘·스타일 편향을 제공한다 (OpenAI 공개 명세). 도메인 용어를 선행 주입하는 용도로 사용 가능.
- 모든 회의가 특정 도메인에 속하지 않는다. 일반 팀 미팅 / 잡담성 회의는 glossary를 비활성화해야 한다(과적합 방지).
- Fact-Checker 패널이 고유명사 오인식에 가장 민감하다. 잘못 인식된 단어로 팩트체크 호출 시 틀린 결과가 생성된다.
- 사용자는 동일 도메인 회의를 반복 개최한다. 매 회의마다 인터뷰를 요구하는 것은 마찰을 유발한다.
- CLAUDE.md: 프롬프트는 `prompts/*` 외부 파일로 분리한다. 용어집도 동일 원칙(외부 편집 가능한 구조화 파일)을 따른다.
- DR-04 화이트리스트: CLI에 전달되는 데이터는 롤링 버퍼 텍스트에 한정. 용어집 텍스트는 **구성 데이터**로 동일 경로 취급한다 (개인정보 포함 금지).
- 본 DR의 범위: 설계 원칙·데이터 구조·통합 지점·검증 방법 확정. 실제 구현은 Phase P2 이후.

## 2. 작업 가설 (Working Hypothesis)

**3-tier 용어집 + 1회성 세션 시작 인터뷰 + 4개 적용 지점.**

### 2.1 3-tier 용어집 계층

| 티어 | 이름 | 수명 | 용도 |
|------|------|------|------|
| T1 | **도메인 프로파일** | 영구 (YAML 파일) | 재사용 가능한 도메인 (예: 크립토 차익거래) |
| T2 | **세션 전용 용어** | 회의 1회 (메모리) | 1회 게스트 이름, 특정 프로젝트 코드명 |
| T3 | **런타임 학습 후보** | 회의 중 수집, 종료 후 사용자 승인 시 T1로 승격 (P4 이상) | 오인식 반복 단어 자동 감지 |

MVP는 T1 + T2만 구현. T3은 후속 로드맵.

### 2.2 도메인 프로파일 파일 구조 (`config/glossaries/<domain>.yaml`)

```yaml
domain: crypto_arbitrage          # 파일 식별자 (kebab/snake)
display_name: "크립토 차익거래"     # UI 표시용
parent: crypto                     # 옵셔널 상속. 상위 glossary의 terms를 합쳐 사용
prompt_hint: "이 회의는 크립토 차익거래 전략 논의입니다. 주요 거래소·전략·지표 용어가 자주 등장합니다."
terms:
  - canonical: 바이낸스
    aliases: [파이넌스, 비나스]       # Whisper 오인식 패턴 실측 기록
    category: exchange
  - canonical: 차익거래
    aliases: [차잇거래]
    category: strategy
  - canonical: 펀딩비
    aliases: []
    category: metric
  - canonical: 하이퍼리퀴드
    aliases: []
    category: exchange
```

- `prompt_hint`: 패널 프롬프트 상단 주입용 1문장(컨텍스트). Whisper에도 일부 사용.
- `aliases`: **실측에 기반해 누적하는 오인식 패턴**. 후처리 보정의 원천.
- `category`: 미래 필터링용 (예: Fact-Checker는 `metric` 위주). MVP는 기록만.
- `parent`: 상위 도메인 상속. 예: `crypto_arbitrage`의 parent가 `crypto`면 거래소·지표 공통 용어를 중복 작성하지 않음.

### 2.3 프로파일 인덱스 (`config/profiles.yaml`)

```yaml
profiles:
  - name: "내 팀 주간 회의"
    glossary: crypto_arbitrage
    last_used: 2026-04-22T15:30:00+09:00
  - name: "ENG 스탠드업"
    glossary: engineering
    last_used: 2026-04-20T10:00:00+09:00
default: "내 팀 주간 회의"   # 자동 로드 대상. 없으면 매번 선택 화면
```

### 2.4 세션 시작 인터뷰 플로우

```
앱 실행
  │
  ├─ profiles.yaml.default 존재?
  │    ├─ Yes → default 자동 로드 + "다른 프로파일 사용" 버튼만 노출 (3초 타임아웃)
  │    └─ No  → 프로파일 선택 화면
  │
  ├─ 프로파일 선택 화면:
  │    [A] 저장된 프로파일 (목록)
  │    [B] 새 프로파일 만들기 → 인터뷰
  │    [C] 일반 회의 (glossary off)
  │
  ├─ [B] 선택 시 인터뷰 (3문항, 예상 90초):
  │    Q1. 도메인 카테고리: [프리셋 10개 + "기타 직접 입력"]
  │    Q2. 회의 컨텍스트 1문장 (prompt_hint로 저장)
  │    Q3. 주요 고유명사 (쉼표 구분, 최대 30개, 생략 가능)
  │
  ├─ 저장 여부:
  │    - "이번만 사용" → T2 (세션 전용, 파일 미저장)
  │    - "프로파일 저장" → 이름 입력 → T1 (YAML 생성)
  │
  ├─ 세션 시작 전 "추가 세션 전용 용어" 입력 (옵션, T2 누적)
  │
  └─ 회의 시작
```

**재사용 최적화:** 기본 흐름은 "지난 프로파일 자동 로드 → Enter로 시작". 인터뷰는 최초 1회만.

### 2.5 4개 적용 지점

| # | 적용 지점 | 주입 내용 | 근거 |
|---|----------|-----------|------|
| 1 | **Whisper `initial_prompt`** | `prompt_hint` + `terms[].canonical` 상위 N=20개 | STT 단계에서 도메인 어휘 편향 |
| 2 | **후처리 보정** | `aliases → canonical` 치환 (정규식 워드 경계) | `initial_prompt`로 잡히지 않은 잔여 오인식 |
| 3 | **Fact-Checker 프롬프트** | `display_name` + `prompt_hint` + 전체 terms 리스트 (category='metric','entity' 우선) | 정확한 수치·고유명사 판단 |
| 4 | **Summarizer / Ideator / Devil's Advocate 프롬프트** | `prompt_hint`만 (terms 리스트 제외) | 컨텍스트 제공, 토큰 절약 |

## 3. 이유 (Rationale)

**3-tier 분리 근거**
영구 저장 가치가 없는 1회성 게스트 이름(T2)을 T1에 섞으면 파일이 지저분해지고, 반대로 반복 용어를 매번 T2로 입력하면 마찰이 크다. 수명 기반 분리가 자연스럽다. T3(자동 학습)은 사용자 승인 없이 용어집을 자동 확장하면 잘못된 학습이 누적될 위험이 있어 후속 단계로 미룬다.

**YAML 포맷 선택 근거**
사용자가 에디터로 직접 수정 가능해야 한다(용어 추가·삭제). JSON은 주석 불가, TOML은 중첩 리스트 가독성 낮음. YAML은 CLAUDE.md의 `config/triggers.yaml` 설계(DR-05)와도 일관된다.

**`initial_prompt` + 후처리 이중 방어 근거**
실측에서 `medium`도 "바이낸스"를 복구하지 못했다. `initial_prompt`로 완전 해결된다는 보장이 없으므로, `aliases` 후처리를 **안전망**으로 병행한다. 단, 후처리만으로는 처음 보는 오인식 패턴을 못 잡으므로 `initial_prompt`가 1차 방어선.

**토큰 한도 N=20 선택 근거**
Whisper `initial_prompt`는 ~224 토큰 한도. 한글 고유명사는 평균 3~4 토큰으로 가정 시 20개 = 60~80 토큰. 여기에 `prompt_hint` 1문장(~40 토큰)을 더해도 여유. 실측 후 조정.

**parent 상속 근거**
"크립토" 도메인에 공통인 용어(바이낸스, 펀딩비)를 하위 전략별 파일마다 중복 작성하면 유지보수 부담. 상속으로 공통을 `crypto.yaml`에 두고 `crypto_arbitrage.yaml`이 특화 용어만 추가.

**Fact-Checker만 전체 terms 주입 근거**
Summarizer/Ideator/Devil's Advocate는 "무엇이 사실인가"를 판단하지 않는다. 이들에게 긴 용어 리스트를 주입하면 1줄 50자 출력 제약에 오히려 방해. `prompt_hint` 1문장으로 충분.

**자동 로드 기본값 근거**
동일 팀의 반복 주간 회의가 주 사용 시나리오. 매번 5개 화면을 거치면 앱 기동 비용이 회의 시작을 늦춘다. "지난 프로파일 → Enter로 시작" 2스텝이 기본이어야 한다.

**개인정보 배제 원칙**
참석자 실명·이메일·계좌번호 등은 용어집에 포함하지 않는다(DR-04 S-7 준수). 용어집은 **도메인 공용 어휘**만 담고, 참석자 고유정보가 필요한 경우 T2(세션 전용)로만 관리하여 파일 미저장.

## 4. 검증 방법 (Verification)

### 4.1 STT 정확도 (initial_prompt 적용 전후)

**측정 대상:** 기존 실측 WAV (`samples/stt_test.wav`, 24초, 크립토 차익거래 발화 4문장)

| 지표 | 통과 기준 | 측정 방법 |
|------|----------|----------|
| "바이낸스" 복구율 | 5회 전사 중 ≥ 4회 | small 모델 + initial_prompt 적용 후 재전사 |
| "차익거래" 복구율 | 5회 전사 중 ≥ 4회 | 동일 |
| 정상 단어 regression | ≤ 5% (정확했던 단어 중 5% 이하만 오염) | 원본 전사와 diff |
| 추가 할루시네이션 건수 | ≤ 1건/30초 | 육안 검사 |

**통과 기준:** 4항목 전체 통과 시 DR-07 STT 경로 확정.

### 4.2 후처리 보정 정확도

**측정 대상:** `aliases` 기반 치환 후 결과

| 지표 | 통과 기준 |
|------|----------|
| alias → canonical 치환 성공률 | = 100% (alias가 워드 경계로 감지되면 반드시 치환) |
| 오치환 (alias가 아닌 단어를 치환) | = 0건 |

**측정 방법:** `config/glossaries/crypto_arbitrage.yaml`의 alias 목록 기반 유닛 테스트. 한국어 조사 경계 처리 특수 주의(예: "차잇거래의" → "차익거래의").

### 4.3 인터뷰 플로우 UX

| 지표 | 통과 기준 | 측정 방법 |
|------|----------|----------|
| 최초 인터뷰 완주 시간 | 평균 ≤ 90초 (3문항) | 사용자 5명 스톱워치 |
| 재사용 시 회의 시작까지 | ≤ 10초 (default 자동 로드 포함) | 동일 |
| 인터뷰 스킵 가능 경로 | [C] 일반 회의 선택 시 0문항으로 진입 가능 | 수동 체크 |

### 4.4 프로파일 저장·로드 무결성

- YAML 저장 후 프로세스 재시작 → 동일 glossary 로드 확인 (`diff` 0 바이트)
- `parent` 상속 해석 정확성: `crypto_arbitrage` 로드 시 `crypto`의 terms 포함 여부 확인

## 5. 탈락 시 대안 (Fallback)

### 5.1 `initial_prompt`가 복구에 실패

**원인 후보:** 모델이 학습 과정에서 해당 단어를 거의 못 봤거나, 사용자 발음이 표준형과 심하게 다름.

- **플랜 A:** `aliases` 후처리에 전적으로 의존. 사용자가 오인식 패턴을 `aliases`에 누적 추가.
- **플랜 B:** Fact-Checker 프롬프트에 "주의: '파이넌스'는 '바이낸스'의 오인식일 가능성"을 명시 주입. LLM 맥락 판단으로 교정.
- **플랜 C:** Fact-Checker 트리거 시에만 `large-v3`로 재전사 (해당 청크만). CPU에서 `large-v3`가 실시간보다 느리면 제외.

### 5.2 인터뷰가 팀에게 마찰로 느껴짐

- **플랜 A:** Q3(용어 입력)을 필드로만 남기고 필수 질문에서 제외. Q1·Q2만으로 프로파일 생성 허용.
- **플랜 B:** "2번째 회의부터 자동 로드" 기본값을 "1번째 회의부터 default 설정 제안"으로 강화. 최초 인터뷰 후 "이 설정을 다음에도 기본으로?" 1클릭 승격.

### 5.3 용어집이 할루시네이션 유발

**증상:** `initial_prompt`에 주입된 용어가 실제 발화에 없는데 전사에 삽입됨.

- **플랜 A:** `initial_prompt`의 terms 수를 N=20 → N=10으로 축소.
- **플랜 B:** terms 리스트를 문장형이 아닌 **쉼표 구분 명사 나열**로 포맷 변경 (스타일 편향 감소).
- **플랜 C:** `prompt_hint`만 주입, terms는 후처리(`aliases`)로만 처리.

### 5.4 용어집 YAML 스키마 불일치 / 파싱 오류

- **플랜 A:** 앱 시작 시 스키마 검증(pydantic). 오류 발생 시 해당 프로파일 건너뛰고 일반 회의 모드로 진입, 콘솔에 경고.
- **플랜 B:** `EXAMPLE.yaml` 템플릿 제공. 사용자가 복사 수정하도록 유도.

### 5.5 개인정보 혼입 감지

**증상:** 사용자가 실수로 참석자 실명·계좌·전화번호 등을 용어집에 추가.

- **플랜 A:** 저장 시점에 정규식 민감정보 필터(DR-04 Phase 1 필터 재사용) 적용 → 해당 용어 거부 + 사용자 경고.
- **플랜 B:** 용어집 파일 경로를 `.gitignore`에 자동 추가(DR-00b 규약 준수).

## 6. 영향받는 DR / CONSISTENCY

- **DR-03 (STT 모드):** `initial_prompt` 주입 경로 추가. STT 단계가 glossary 로드에 의존하므로 선후관계 명시 필요.
- **DR-04 (데이터 흐름):** 용어집 텍스트도 CLI 전송 영역 화이트리스트에 포함. 단, 개인정보 금지 조항 명시 필요. S-7(간접 식별 정보) 체크리스트에 용어집 검증 항목 추가.
- **DR-05 (트리거 빈도):** 영향 없음. 용어집은 트리거 빈도를 바꾸지 않음.
- **DR-06 (UX):** 인터뷰 UI는 Phase 0 spike 이후 Frontend Developer 설계. 본 DR은 플로우만 확정.
- **CLAUDE.md 정합성:** "프롬프트는 `prompts/` 외부 파일" 원칙을 `config/glossaries/` 확장으로 계승. 새 규칙 추가 불필요.
