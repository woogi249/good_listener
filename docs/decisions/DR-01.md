# DR-01: Claude CLI 동시 호출 가능성

**상태:** 작업 가설 (Phase 0 spike 전)
**작성일:** 2026-04-19
**선행 조건:** DR-00b (rate limit 검증 통과)

---

## 1. 가정 (Assumption)

- DR-00b에서 시간당 60회 호출이 rate limit 에러 없이 통과했음을 전제로 한다.
- `claude -p "프롬프트"` 방식이 기본 호출 형식이며, stdin pipe도 동일 조건으로 동작한다고 가정한다.
- 단일 Pro/Max 계정을 팀 전원이 공유하는 구조다. 개인별 별도 계정을 사용하는 구조가 아니다.
- `claude` CLI는 OS 프로세스로 스폰되므로 동시 N개 실행 시 N개의 독립 자식 프로세스가 생성된다.
- 패널 4개(A 요약, B 팩트체크, C 아이디어, D-3 반박)가 동일한 짧은 시간 창(수 초 이내)에 동시에 트리거될 수 있는 최악 시나리오를 가정한다.
- 의존성: DR-00b (rate limit). 이 DR의 결론은 DR-05(트리거 설계)와 DR-02(레이턴시 측정 방법론)에 직접 영향을 준다.

---

## 2. 작업 가설 (Working Hypothesis)

**순차 큐 + 우선순위 기반, 동시 최대 2개 프로세스** 모델을 채택한다.

4개 패널이 동시 트리거될 때 최대 2개 CLI 프로세스를 병렬 실행하고, 나머지 2개는 우선순위 큐에서 대기한다. 완전 병렬(4개 동시)보다 예측 가능한 레이턴시와 rate limit 마진을 확보하는 것이 "실시간성"보다 중요한 우선순위라고 판단한다.

우선순위 규칙 초안:
- **HIGH**: Fact-Checker(B) — 오류 정보가 발화 직후 교정되어야 하므로 긴급, Summarizer(A) — 항상 최신 맥락 유지 필요
- **MED**: Devil's Advocate(D-3) — 합의 신호 직후 반박 시점이 중요하나 수 초 지연 허용
- **LOW**: Ideator(C) — 교착 감지 후 아이디어 제안이므로 수십 초 지연도 사용 가능

이 가설은 Phase 0 spike 측정 결과에 따라 확정 또는 기각된다.

---

## 3. 이유 (Rationale)

**4개 완전 병렬의 위험**

동시에 4개 CLI 프로세스를 스폰하면 순간적으로 rate limit 윈도우를 소진할 가능성이 있다. DR-00b가 검증하는 기준은 분산된 60회/시간이지, 순간 4회 동시 버스트가 아니다. Anthropic의 rate limit가 슬라이딩 윈도우 방식이라면 단시간 내 다수 호출이 제한 발동 조건에 해당할 수 있다. 또한 4개 프로세스의 초기화 오버헤드가 합산되어 첫 응답까지 체감 지연이 오히려 늘어날 수 있다.

**순차 직렬만의 위험**

4개를 완전 직렬로 처리하면 최악 시나리오에서 4 × 평균 응답 시간이 합산된다. 평균 CLI 응답을 5초로 가정하면 최악 20초 지연이 발생하며, 이는 AGENTS.md의 "실시간" 요건과 충돌한다.

**동시 2개 + 우선순위 큐 절충**

최악 시나리오에서도 HIGH 패널 2개가 먼저 병렬 처리되고, 나머지 2개는 1라운드(약 5초) 후 처리된다. 즉 최악 대기 시간이 2 × 평균 응답 시간(약 10초)으로 줄어든다. rate limit 측면에서도 동시 2개는 4개 대비 순간 버스트 부담이 절반이다. 이 모델은 구현 복잡도(단순 세마포어 기반 풀)도 낮다.

**AGENTS.md 비용 원칙과의 정합성**

CLAUDE.md의 최상위 원칙은 비용 최소화다. 동시성을 제한하면 불필요한 과호출을 억제하고, 큐 기반 구조는 쿨다운 강제 실행 지점을 명확히 제공한다.

## 4. 검증 방법 (Verification)

- **측정 도구**: Python `concurrent.futures.ThreadPoolExecutor` 또는 `asyncio.gather`로 `claude -p` 동시 N개 호출. `time.perf_counter`로 각 호출의 시작·종료 시각 기록.
- **측정 횟수 (N)**: 동시성 수준 1/2/3/4개별 각 10회 반복, 총 40세트. 세트 간 간격 30초(rate limit 윈도우 리셋 여유).
- **대표값**: 각 동시성 수준별 p50 응답 시간, p95 응답 시간, 실패율(returncode ≠ 0 또는 stderr에 rate limit 키워드 포함).
- **환경 조건 (고정)**: `CONSISTENCY.md §3.7 공통 환경 조건` 참조. 변경 시 세 DR(00b/01/02) 동시 갱신 필수.
  - DR-01 특이 조건: 동시성 수준 1/2/3/4별 각 10라운드, 세트 간 30초, 프롬프트는 DR-00b와 동일 500토큰 텍스트.
- **측정 스크립트 스켈레톤 (의사코드)**:

```python
# 의사코드 — 실제 파일로 생성 금지, DR 문서 내 기술 전용

import concurrent.futures, subprocess, time

PROMPT = "<롤링 버퍼 10발화 모의 텍스트, ~500토큰>"
CONCURRENCY_LEVELS = [1, 2, 3, 4]
ROUNDS_PER_LEVEL = 10

def call_claude(_):
    # SECURITY (CONSISTENCY.md S-1): stdin pipe 사용, 프로세스 명령줄 노출 방지
    start = time.perf_counter()
    result = subprocess.run(
        ["claude", "-p", "-"],
        input=PROMPT,
        capture_output=True, text=True, timeout=30
    )
    elapsed = time.perf_counter() - start
    return {
        "success": result.returncode == 0,
        "elapsed_s": elapsed,
        "stderr_snippet": result.stderr[:200]
    }

for concurrency in CONCURRENCY_LEVELS:
    round_results = []
    for _ in range(ROUNDS_PER_LEVEL):
        with concurrent.futures.ThreadPoolExecutor(max_workers=concurrency) as pool:
            results = list(pool.map(call_claude, range(concurrency)))
        round_results.extend(results)
        time.sleep(30)  # 세트 간 rate limit 윈도우 리셋 여유

    # p50 / p95 / 실패율 집계 후 출력
```

- **수집 지표**: 각 호출의 시작/종료 시각, stdout 성공 여부, stderr 에러 메시지 원문.
- **통과 기준 (정량)**:
  - **동시 2개**: p95 ≤ 7초 AND 실패율 0% → 작업 가설 **확정** (2개 병렬 큐 모델 채택)
  - **동시 4개**: p95 ≤ 10초 AND 실패율 ≤ 5% → 가설 **강화** (완전 병렬도 가능 — DR-05 트리거 설계 단순화 검토)
  - **실패율 > 20% 또는 rate limit 에러 1회 이상 (어느 수준에서든)**: 가설 **기각** → 섹션 5 Fallback 진입

---

## 5. 탈락 시 대안 (Fallback)

**탈락 조건**: 동시 2개 수준에서 p95 > 7초 또는 실패율 > 0%

- **완전 병렬 가능 판정 (동시 4개 통과)**:
  - **선행 게이트 (필수)**: DR-00b를 **순간 버스트 시나리오**로 재실행해야 한다. 기존 DR-00b는 분당 1회 분산 호출만 검증했으므로, 4개 동시 스폰 × 10분 = 40회 버스트 패턴에서도 성공률 ≥ 95%를 확인하지 못하면 이 Fallback 경로 진입 금지.
  - 위 게이트 통과 후에만: 우선순위 큐 생략, 패널 4개를 독립 워커로 스폰.
  - DR-05 트리거 설계 단순화: 큐 대기 없이 각 패널이 자체 쿨다운만 관리.
  - DR-02 레이턴시 측정 기준값을 4개 병렬 p95 기준으로 재설정.
  - DR-05의 `rate_limit_headroom` 계수를 재계산하여 쿨다운 공식에 반영.

- **동시 1개만 가능 판정 (직렬 강제)**:
  - 엄격 순차 큐 도입. 패널별 쿨다운을 최소 60초 이상으로 확대.
  - 패널 수 축소(Summarizer + Fact-Checker 2개 실시간, 나머지 사후 처리) 검토.
  - DR-05 트리거 설계: 패널 간 트리거 억제(동시 발동 방지) 로직 필수화.

- **Rate limit 조기 도달 (DR-00b 재실행 필요)**:
  - DR-00b를 더 낮은 빈도(시간당 30회)로 재실행. 통과 여부 재판정 후 DR-01 재검증.
  - AGENTS.md의 쿨다운 기본값을 30초 → 60초로 상향 후 DR-01 재실행.

- **영향받는 DR**:
  - **DR-05 (트리거 설계)**: 동시성 모델 결론에 따라 트리거 억제 로직과 쿨다운 공식이 근본적으로 달라짐. DR-01 확정 전 DR-05 작성 금지.
  - **DR-02 (레이턴시 측정)**: 동시 호출 시 개별 응답 시간이 직렬 대비 늘어날 수 있으므로, DR-01 결과를 DR-02 환경 조건에 반영 후 재측정 필요.
