# DR-05: 트리거 조건 구현 전략

**상태:** 작업 가설 (Phase 0 spike 전)
**작성일:** 2026-04-19
**선행 조건:** DR-01 (CLI 동시 호출 모델), DR-04 (데이터 흐름 경계)

---

## 1. 가정 (Assumption)

- DR-01에서 동시 최대 2개 CLI 프로세스 + 우선순위 큐(Summarizer·Fact-Checker = HIGH) 모델이 확정되었음을 전제로 한다.
- DR-04에서 CLI 전송 허용 데이터는 롤링 버퍼(직전 10~20발화) 텍스트로 제한되었음을 전제로 한다. 민감정보 블랙리스트 훅이 Phase 1 코드 내 예약 상태임도 전제한다.
- DR-02에서 CLI 왕복 레이턴시 p50 3초 / p95 5초가 가설로 제시되었음을 전제로 한다. 트리거 쿨다운 공식은 이 수치를 변수로 사용하며, 실측 후 자동 연동된다.
- 1회 회의 1시간 기준 예상 CLI 호출 총량 ≤ 40회로 rate limit 마진을 확보한다(분당 평균 ≤ 0.67회, DR-00b 통과 기준인 시간당 60회의 67% 이하).
- 트리거 평가 자체(룰 판정)는 CLI 호출 없이 로컬에서만 수행한다. CLI는 트리거가 발동된 이후에만 호출된다.
- 의존성: DR-01 (strict — 동시성 슬롯 수가 쿨다운 공식에 영향), DR-04 (strict — 전송 가능 데이터 범위 제한).

## 2. 작업 가설 (Working Hypothesis)

**룰 기반 트리거 + YAML 외부 설정 파일** 방식을 채택한다.

패널별 독립 트리거 룰을 `config/triggers.yaml`로 외부화한다. 각 룰은 **(조건 평가자, 쿨다운, 우선순위)** 3요소로 구성되며, CLI 호출 없이 CPU 연산만으로 즉시 판정한다(< 1ms 목표).

**동적 쿨다운 공식**: 고정값 대신 DR-02/DR-03 실측 결과 + DR-00b rate limit 여유를 모두 반영하는 공식을 사용한다.

```
base(초)     = max(30, 3 × (STT_p95 + CLI_p95))
쿨다운(초)   = base × rate_limit_headroom

rate_limit_headroom =
  1.0   if DR-00b 성공률 ≥ 95% (통과)
  1.5   if DR-00b 성공률 85~94% (회색 영역)
  2.0   if DR-00b 성공률 < 85% OR 순간 버스트 에러 관찰 (탈락 근처)
```

DR-02 가설(CLI p95 = 5초), DR-03 가설(STT p95 = 3초), DR-00b 통과 전제 시 초기값 `max(30, 3×8) × 1.0 = 30초`. DR-00b가 회색 영역으로 판정되면 45초로 자동 연장되어 큐 적체와 rate limit 마진 소진을 동시에 방지한다. 실측 수치가 커지면 base 자체가 연장되고, headroom 계수로 추가 완충된다.

**공식 vs 패널별 초기값의 관계 (CONSISTENCY.md C-2)**: 동적 쿨다운 공식은 **패널 공통 하한선**(base × headroom)을 산출한다. 아래 패널별 초기 룰 테이블의 쿨다운은 하한선 이상 범위에서 패널 긴급도에 따라 설정한 값이며, `config/triggers.yaml`에서 개별 튜닝 가능하다. 규칙:

- **Fact-Checker (B)** = `하한선 × 1` (긴급 — 오류 즉시 교정 필요, 30초)
- **Summarizer (A)** = `하한선 × 2` (맥락 유지, 60초)
- **Devil's Advocate (D-3)** = `하한선 × 3` (합의 직후 잠깐의 반성 허용, 90초)
- **Ideator (C)** = `하한선 × 4` (교착 후 수십 초 지연 허용, 120초)

하한선이 실측으로 45초로 상향되면 각 패널의 초기값도 비례로 갱신된다(B=45, A=90, D-3=135, C=180). `config/triggers.yaml`에서 배수만 유지하면 상향에 자동 동기화.

**패널별 초기 룰**

| 패널 | 트리거 조건 | 평가자 | 쿨다운 | 우선순위 |
|------|------------|--------|--------|----------|
| A Summarizer | 10발화 누적 OR 주제 키워드 시프트 감지 | 발화 카운터 + TF-IDF 코사인 유사도 < 0.4 | 60초 | HIGH |
| B Fact-Checker | 숫자·단위·고유명사 포함 발화 | 정규식 + KoNLPy NER | 30초/패턴 | HIGH |
| C Ideator | 3분 경과 결론 없음 OR 동일 단어군 반복 | 타이머 + n-gram 반복도 > 0.3 | 120초 | LOW |
| D-3 Devil's Advocate | 합의 신호 키워드 감지("그럼 ~하자", "OK", "확정") | 키워드 목록 매칭 | 90초 | MED |

이 가설은 Phase 0 검증 결과에 따라 확정 또는 기각된다.

## 3. 이유 (Rationale)

**룰 기반을 선택한 이유**

경량 분류 모델(BERT-small 등) 도입이 대안이나, 두 가지 이유로 Phase 1 범위를 초과한다. 첫째, 로컬 GPU를 Whisper(DR-03)와 공유하면 STT 레이턴시 예산(p95 3초)을 침범할 위험이 있다. 둘째, 한국어 회의 도메인에 맞게 파인튜닝된 공개 모델이 없어 직접 학습 데이터 구축이 필요하며 이는 Phase 1 공수를 초과한다. 룰 기반은 CPU 전용, 즉시 판정, 재배포 없이 YAML 튜닝 가능이라는 세 가지 이점이 있다.

**YAML 외부화 이유**

회의 유형(연구/기획/일상)에 따라 "교착"의 기준이 다르다. 예를 들어 연구 회의에서는 30분 결론 없음도 정상이지만 일상 업무 회의에서는 3분이 한계일 수 있다. YAML로 파라미터를 노출하면 재배포 없이 현장 튜닝이 가능하며, DR-00a 수요 검증에서 확인된 팀별 선호도 차이를 반영하기 쉽다.

**동적 쿨다운 공식 이유**

AGENTS.md의 "쿨다운 30초" 고정값은 DR-02/DR-03 실측치와 무관하게 설정된 값이다. CLI 응답이 p95 5초보다 느려지면 큐가 쌓이는 동안 새 트리거가 계속 발동되어 호출이 폭주할 수 있다. 공식 `max(30, 3×(STT_p95+CLI_p95))`은 실측 결과를 자동 반영하여 이 위험을 제거하면서, 하한선 30초로 지나친 침묵도 방지한다.

**우선순위 배치 이유**

DR-01의 동시 2슬롯을 HIGH 패널(A·B)이 우선 점유함으로써, 사실 오류 정정(B)과 맥락 요약(A)이 회의 흐름에서 가장 시급한 시점에 처리된다. C(Ideator)는 교착 이후 수십 초 지연도 허용되며, D-3(Devil's Advocate)는 합의 직후이지만 취소 불가한 결정이 나기 전 MED 수준 대기가 적절하다.

**DR-04 화이트리스트 준수**

트리거 평가자가 판정에 사용하는 데이터는 모두 롤링 버퍼 텍스트 범위 내이다. 키워드 매칭, TF-IDF, n-gram 모두 발화 텍스트만 소비하며 원본 오디오나 전체 트랜스크립트에 접근하지 않는다.

## 4. 검증 방법 (Verification)

- **측정 도구**: 한국어 회의 녹음 3종(DR-03 샘플 재사용)을 STT 변환한 트랜스크립트를 입력으로 사용. 트리거 평가자 단위 테스트(pytest) + 전체 파이프라인 재생 통합 테스트.
- **측정 횟수 (N)**: 15분 녹음 × 3종 = 총 45분 분량. 각 샘플에서 트리거 발화 총합을 기록.
- **대표값**:
  - 분당 평균 트리거 수 (패널별 및 전체 합산)
  - 큐 깊이 p95 (동시 대기 중인 CLI 호출 개수)
  - 트리거 정확도 (수동 라벨 대비 패널별 precision / recall)
- **환경 조건 (고정)**:
  - DR-00c 확정 하드웨어
  - `config/triggers.yaml` 기본값 고정 1세트 (튜닝 없이 초기값 그대로)
  - 동일 3종 샘플 반복 (DR-03와 동일 파일)
  - DR-01 확정 동시성 모델(최대 2슬롯) 유지
- **통과 기준 (정량)**:
  - 분당 **실제 CLI 호출** ≤ 2회 (1시간 기준 ≤ 40회 등가). 쿨다운으로 억제된 평가 통과(`cooldown_hit=True`)는 제외. 의사코드의 `actual_cli_calls_per_minute` 지표 기준.
  - 큐 깊이 p95 ≤ 3 (2슬롯 + 대기 1개 이내)
  - 패널별 precision ≥ 70% (적절한 시점 판정 기준)
  - "폭주" 정의 — 10초 윈도우 내 동시 발화 4건 이상: 발생 0건
- **수집 지표**: 트리거 발동/미발동 로그, 쿨다운 히트 비율, 큐 대기 시간 분포, 오발동·미발동 사례 원문.

**검증 의사코드**

```python
# 의사코드 — 실제 파일로 생성 금지, DR 문서 내 기술 전용

transcript = load_transcript("sample_01.txt")  # 15분, ~180발화
trigger_log = []

for utterance in transcript:
    for panel in [summarizer, fact_checker, ideator, devils_advocate]:
        if panel.evaluate(utterance):          # 룰 평가, < 1ms
            trigger_log.append({
                "panel": panel.name,
                "time": utterance.timestamp,
                "cooldown_hit": panel.in_cooldown()
            })
            if not panel.in_cooldown():
                queue.enqueue(panel, priority=panel.priority)

# 결과 집계 (CONSISTENCY.md C-5: 평가 통과와 실제 CLI 호출을 분리)
evaluations_per_minute = len(trigger_log) / 15                                  # 쿨다운 억제 포함 전체 평가 통과 횟수
actual_cli_calls_per_minute = len([t for t in trigger_log if not t["cooldown_hit"]]) / 15  # 실제 CLI 호출 빈도 (본 DR 통과 기준)
queue_depth_p95 = percentile(queue_depth_samples, 95)
precision = manual_labels.compare(trigger_log)  # manual_labels = load_labels("sample_01_labels.json")
```

## 5. 탈락 시 대안 (Fallback)

**분당 평균 트리거 > 2회 (폭주) 시**
- 플랜 A: 쿨다운 공식 계수 상향 `3×` → `5×(STT_p95 + CLI_p95)`
- 플랜 B: 패널 수 축소 — Ideator(C) 제외, 3패널로 Phase 1 범위 축소. C는 Phase 2로 이관.

**패널별 precision < 70% 시**
- 플랜 C: `config/triggers.yaml` 룰 재튜닝 + 회의 샘플 증강(3종 → 5종 이상)
- 플랜 D: 경량 분류 모델 도입 — Phase 2로 이관, Phase 1은 플랜 B(3패널)로 임시 운영

**큐 적체 지속 시**
- DR-01 동시성 가설 재검증: 병렬 슬롯을 2 → 4로 확장 시도. DR-01 섹션 5 Fallback("완전 병렬 가능 판정") 경로 진입.

**DR-04 민감정보 훅 발동 시**
- 해당 발화는 트리거 평가 자체를 스킵하고 다음 발화에서 재평가. 스킵된 발화는 발화 카운터(Summarizer용)에서도 제외.

**영향받는 DR**
- **DR-01**: 동시성 재협상이 필요할 경우 DR-01 섹션 5 Fallback 참조 후 공동 재작성.
- **DR-02**: 큐 대기 시간이 end-to-end 레이턴시에 추가되므로, 트리거 폭주 수정 이후 DR-02 레이턴시 예산 재배분 검토.
- **DR-06**: UI에 트리거 발동 빈도 표시(패널별 마지막 갱신 시각) 요건이 있으므로, 트리거 로그 인터페이스 변경 시 DR-06과 공동 조정 필요.
